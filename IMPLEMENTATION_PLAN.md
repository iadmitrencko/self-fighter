# Self-Fighter — план реалізації MVP

**Основа:** `PROJECT_SPECIFICATION.md` v1.3 і макети з `design/`.
**Дата:** 2026-10-30, оновлено 2026-11-02 (R21). Версії стеку та їх сумісність перевірені в реєстрах пакетів 2026-10-30.
**Оцінки:** орієнтовні, у робочих днях одного розробника.

---

## 1. Ключова ідея

Гра працює без реєстрації, а дані кожного користувача зберігаються в MySQL (§15). Гість теж є користувачем: браузер знаходить його за cookie пристрою. Необов'язковий вхід через Google додає до того самого користувача спосіб входу й відкриває його дані на інших пристроях (§23). Реєстрацію за email і паролем додамо пізніше як ще один спосіб входу.

| Шар | Технологія | Відповідальність |
| --- | ---------- | ---------------- |
| Публічні сторінки | Symfony + Twig | Лендінг, контент, готові виклики |
| Гра | React + TypeScript | Екрани тренування та правила режимів |
| Дані користувачів | MySQL через API | Вправи, історія й налаштування гостей і облікових записів |
| Буфер у браузері | `localStorage` | Поточна спроба й завершені спроби, що чекають надсилання |
| Серверні дані | MySQL | Каталог, контент, події |

Наслідки:

- Правила гри існують лише в TypeScript, дублювання в PHP немає.
- Формат даних змінюють міграції на сервері. Браузер не зберігає даних, які довелося б мігрувати після релізу.
- Екрани гри працюють із контрактом сховища й не знають, як влаштоване API (розділ 3.7).
- Індексовані сторінки не залежать від виконання JavaScript, не запускають сесію й не читають cookie.
- Розпочате тренування не потребує сервера.

### 2.2 Закриті прогалини специфікації

| # | Прогалина | Рішення |
| --- | --------- | ------- |
| R6 | §6.6 і §12.3 згадують нічию у вправі, а правила §6.5 і §7.4 її не передбачають. | Вправа має два результати: перемога або поразка. Рівний результат за «Перевиконати» є поразкою, як і в макетах. Підрахунок раунду все одно ігнорує нічию, тож §6.6 виконується. |

## 3. Архітектура

### 3.1 Схема

```text
Браузер
├── Публічні сторінки (HTML із Twig, мінімум JS)
└── Гра (React) ──── localStorage: поточна спроба, черга надсилання
        │
        │ сторінки, події, API даних користувача
        ▼
Cloudflare (DNS, CDN)
        ▼
app: FrankenPHP + Symfony ──── MySQL
        │
        └── Google OAuth (лише під час входу)
```

Версії фіксуються в `composer.lock`, `package-lock.json` і тегах образів.

Контент живе в Git (`backend/content/`), а команда `app:content:sync` переносить його в MySQL під час деплою. Адмінки немає: це менше коду й менша поверхня атаки. Готові вправи й конфігурацію відкритого виклику Symfony вбудовує в оболонку гри як JSON, тому окремого API для них немає. Дані користувача гра отримує через API (розділ 3.7).

**Буфер у браузері**

| Ключ `localStorage` | Вміст |
| ------------------- | ----- |
| `activeSession` | Поточна спроба для відновлення після перезавантаження |
| `outbox` | Завершені спроби з `user_id` власника, що чекають надсилання |

Буфер не є сховищем: запис лежить у ньому, доки триває тренування або доки не повернеться зв'язок. Тому браузер його не мігрує. Поточна спроба іншої версії формату відкидається, бо незавершені спроби не зараховуються (§12.4), а спроби з черги сервер приймає як є (розділ 3.7).

Гарантії, закладені в модель:

- Завершена спроба незмінна: API лише додає спроби. Повторний `PUT` із тим самим вмістом нічого не змінює, а інший вміст за тим самим ідентифікатором отримує 409 (§17.2).
- Ідентифікатор спроби (UUID v7) створюється на клієнті під час старту, тому повторне збереження не дублює запис.
- Статистика не зберігається окремо, а щоразу обчислюється зі спроб. Сума перемог, нічиїх і поразок завжди збігається з історією (§14.2).
- Кожен запис містить `schemaVersion`, а час зберігається в UTC.

### 3.6 Ігровий рушій

```ts
// Фіксує конфігурацію, id, час старту і всі значення суперника
createSession(config, { rng, now, newId }): Session

// Індекс поточного етапу або null, якщо спроба завершена
nextStageIndex(session): number | null

// Повторний виклик для заповненого етапу нічого не змінює
submitResult(session, stageIndex, reps): Session

// Створює незмінний запис для історії
finalize(session, finishedAt): Attempt

passesTarget(actual, target, rule)              // over: >, meet: >=
ladderStageRule(target, max, rule)              // верхній етап: meet (R2)
```

Значення суперника генеруються наперед і зберігаються в `activeSession`, тому перезавантаження не змінює вже показаний результат (§7.3). Захист від подвійного натискання працює в рушії, а не лише в кнопці (§12.2). RNG, час і генератор id передаються ззовні, що робить тести детермінованими.

Кожен етап зберігає правило, яке до нього застосовується. Тому R2 живе в одному місці, а підказка на екрані й підрахунок результату не потребують окремої умови для верхнього етапу драбини. `computeFightResult` враховує лише завершені раунди, тож дає і підсумок бою, і рахунок під час гри.

### 3.7 Користувачі й дані

Кожен, хто щось зберіг, є користувачем із `user_id`. Гість відрізняється від облікового запису лише тим, звідки можна дістатися до його даних.

| Користувач | Ідентифікатор | Звідки доступні дані |
| ---------- | ------------- | -------------------- |
| Гість | Токен пристрою в cookie | Лише з цього браузера |
| Вхід через Google | `sub` облікового запису Google | З будь-якого пристрою після входу |
| Вхід через email, пізніше | Підтверджений email | З будь-якого пристрою після входу |

Google знаходимо за `sub`, а не за email: так радить сам Google, бо email облікового запису Google може змінитися. Email у `user` зв'язує вхід через Google з майбутнім входом через email, тож той самий підтверджений адрес не створить другого облікового запису (§23.4).

Cookie пристрою:

- Містить випадковий токен на 256 біт. У MySQL лежить лише його SHA-256, тому витік бази не дає змоги увійти від імені користувача.
- Має `HttpOnly`, `Secure`, `SameSite=Lax` і префікс `__Host-`. Скрипти його не бачать, тож XSS не вкраде токен.
- Живе 400 днів, це максимум Chrome. Сервер продовжує його під час активності, але не частіше разу на добу.
- Сервер ставить його у відповіді HTTP, тому Safari не стирає його через 7 днів без відвідувань, як `localStorage`, IndexedDB і cookie зі скриптів (розділ 10).
- Окремої сесії входу немає: після входу той самий cookie веде до облікового запису.
- Під час входу й виходу токен замінюється новим, тому заздалегідь підкинутий токен не дасть доступу до облікового запису.

Користувачі:

- Гість з'являється під час першого запису через `POST /api/v1/me`, а не під час відвідування. Боти й люди, які лише дивляться, записів не створюють, а створення гостей обмежене за частотою.
- `GET /api/v1/me` повертає поточного користувача разом із власними вправами й налаштуваннями. Тому HTML оболонки не залежить від користувача, а екран налаштування не чекає окремих запитів.
- Гостя, який не користувався застосунком 400 днів, видаляє щоденна команда: його cookie на той час уже не діє.

Вхід:

- Symfony веде користувача на Google через серверний потік Authorization Code зі `state` і PKCE. Запитуємо лише `openid`, `email`, `profile`. `state` і PKCE на час входу лежать у сесії Symfony, яку запускають лише маршрути `/connect/*`. Токени Google не зберігаємо.
- Якщо цей обліковий запис Google ще не використовувався, він додається до гостя цього браузера, а без гостя створюється новий користувач. Гість стає обліковим записом, і дані нікуди не переносяться.
- Якщо обліковий запис Google уже належить іншому користувачу, а гість має спроби чи власні вправи, гра пропонує їх об'єднати (§23.3). Сервер робить це однією транзакцією: спроби змінюють власника, вправи з однаковою назвою зливаються, налаштування облікового запису мають пріоритет. Після відмови дані лишаються в гостя цього браузера. Гість без таких даних просто видаляється.
- `POST /logout` повертає браузер до його гостя, якщо такий лишився, або до стану без користувача.

Дані:

- Екрани працюють лише з асинхронним контрактом `ExerciseStore`, `AttemptStore`, `SettingsStore`. Робоча реалізація звертається до API, а реалізація в пам'яті потрібна для тестів екранів.
- Завершена спроба спершу потрапляє в чергу браузера, а потім надсилається ідемпотентним `PUT /api/v1/attempts/{id}`. Без мережі вона чекає й надсилається пізніше (§15.4). Запис у черзі прив'язаний до `user_id`, тому не потрапить до іншого користувача.
- Формат спроби описує одна JSON Schema в репозиторії. Vitest перевіряє, що кожна спроба з `domain/` їй відповідає, а PHP перевіряє за нею запити. Зміна формату означає нову `schemaVersion` і міграцію Doctrine для наявних записів.
- API приймає записи поточної й попередньої версії формату, тому ні вкладка, відкрита до деплою, ні черга, що чекала мережі, не втрачають даних.
- Правила гри лишаються на клієнті, а сервер перевіряє лише структуру, межі й власника даних. Рейтингів немає, а результат користувач і так вводить сам.
- Змінювальні запити захищені від CSRF: `SameSite=Lax` і перевірка заголовка `Origin`.
- Кожен користувач, зокрема гість, може завантажити свої дані й видалити їх (§15.5). Видалення прибирає всі дані користувача, а `analytics_event.user_id` стає `NULL`.

| Правило | Навіщо |
| ------- | ------ |
| `list()` приймає фільтри й курсор, `stats()` є окремим методом | Сервер не віддає всю історію, статистику рахує SQL |
| Ідентифікатори спроб і власних вправ створюються на клієнті | Повторне надсилання й об'єднання не створюють дублікатів (§17.2) |
| Спроба є самодостатнім JSON із `schemaVersion` | Той самий формат лежить у черзі браузера й у MySQL, а міграція знає версію кожного запису |
| Публічні сторінки не запускають сесію й не читають cookie | Користувачі не погіршують кешування і швидкість SEO-сторінок |
| Користувач, спосіб входу й браузер зберігаються окремо (`user`, `user_identity`, `device`) | Email і пароль додаються пізніше без переробок |

## 4. Docker і Makefile

Для роботи над проєктом на машині потрібен лише Docker. PHP, Composer і Node на хості не використовуються.

| Команда | Дія |
| ------- | --- |
| `make up` | Створює `.env` із `.env.example`, якщо його немає. Виконує `docker compose up -d --build --wait`, встановлює залежності, застосовує міграції, синхронізує контент і друкує адресу |
| `make down` | `docker compose stop`: контейнери й дані лишаються |
| `make kill` | `docker compose down --rmi all --remove-orphans`: видаляє контейнери, мережу та образи проєкту, volume MySQL лишається |

Допоміжні цілі: `help`, `logs`, `ps`, `sh`, `test`, `lint`, `fix`, `migrate`. CI викликає ті самі `make test` і `make lint`, тому локальна перевірка відповідає CI.

Правила:

- `make up` на чистому клоні доводить проєкт до робочого стану без ручних кроків.
- `name: self-fighter` у `compose.yaml` обмежує `make kill` цим проєктом. `docker system prune` не використовуємо.
- Dev-адреси: застосунок `http://localhost:8080`, Vite на порту 5173, MySQL на `127.0.0.1:3307`. Порт 3306 на машині розробки зайнятий іншим проєктом. Порти змінюються через `.env`.
- `vendor/` і `node_modules/` доступні на хості для PhpStorm, але встановлюються лише в контейнерах. `var/` лежить у volume заради швидкодії на macOS.
- Prod-образ збирається багатостадійно: Node будує фронтенд, а фінальна стадія містить код, залежності без dev-пакетів, `public/build` і прогрітий кеш.
- Контейнери `app` і `mysql` мають healthcheck, на який спирається `--wait`.

- Написати політику приватності, умови користування й остаточний текст банера згоди. Політика має описувати cookie пристрою, строк зберігання даних гостя й те, як застосунок використовує дані Google.
- Пройти весь §18 на реальних iPhone та Android.
- Перевірити, що production індексується: немає `noindex`, `robots.txt` не закриває сайт.
- Підключити Search Console і Bing Webmaster Tools, надіслати sitemap.
- Подати застосунок на перевірку бренду Google.

**Готово, коли** всі пункти §18 виконані й головна сторінка доступна для індексації.

## 6. SEO

Технічне SEO лише дає сторінкам змогу потрапити в індекс. Трафік приносять сторінки, що відповідають на запити, які люди вже вводять.

### 6.1 Контент

Назву Self-Fighter поки ніхто не шукає, тому ставка йде на небрендові запити. Приклади нижче є гіпотезами: обсяги пошуку ще не перевірені. Перший крок етапу 7 — звірити їх у Keyword Planner і скоригувати список.

| Тип | Приклади сторінок | Роль |
| --- | ----------------- | ---- |
| Виклики | «100 віджимань», «Драбина віджимань до 10», «100 присідань», «Тренування вдома без інвентарю» | Найсильніший тип: сторінка не лише відповідає на запит, а й одразу запускає тренування |
| Вправи | Віджимання, присідання, підтягування | Техніка, типові помилки, готові тренування |
| Режими | Драбина, випадковий суперник, рівні суперників, ціль | Пояснення методу й приклад |
| Поради | «Як змусити себе тренуватися», «Що таке тренування драбиною» | Інформаційні запити й внутрішні посилання |

На старті це приблизно 45 сторінок, із них близько 30 готових викликів. Кожна сторінка веде в гру, а виклик відкриває її із заповненими налаштуваннями через `/workout/challenge/{slug}`.

Авторські тексти мають бути оригінальними й вичитаними людиною. Тема здоров'я підвищує вимоги до довіри: потрібні автор, сторінка про проєкт, застереження щодо навантажень і посилання на джерела.

### 6.2 Генератор готових викликів

Виклики масштабуються без ручного створення кожної сторінки:

1. `backend/content/challenges/matrix.yaml` описує вправи, режими, обсяги, рівні та реалістичні межі для кожної вправи. Наприклад, драбина підтягувань до 100 не генерується.
2. `frontend/scripts/generate-challenges.ts` розгортає матрицю. Він використовує той самий `domain/`, тому валідація, послідовність етапів і сума повторень не дублюються в PHP.
3. Результат записується в `backend/content/challenges/generated.json` і комітиться, тож кожну зміну видно в PR.
4. `app:content:sync` переносить виклики в MySQL, а Twig будує сторінки.

Сторінка поєднує обчислені дані (етапи, сума повторень), авторські блоки про вправу й режим та унікальний абзац саме про цей виклик.

Google вважає порушенням сторінки, створені під схожі запити, майже однакові сторінки й сторінки, чия мета лише завести відвідувача на сайт. Спосіб створення значення не має: правило діє і для програм, і для людей. Тому для виклику діють обов'язкові критерії:

| Критерій | Як забезпечуємо |
| -------- | --------------- |
| Сторінка корисна без гри: вся програма видна одразу | Шаблон сторінки, функціональний тест |
| Кожна сторінка дає іншу програму, варіанти на кшталт 100 і 105 віджимань не створюються | Крок значень у матриці |
| Є унікальний абзац, вичитаний людиною | Без нього `indexable: false` |
| Текст не дублює сусідні сторінки | Команда `app:content:lint` порівнює тексти й блокує CI |
| Запит має підтверджений попит або сторінка потрібна для навігації каталогом | Поле в матриці, ручна перевірка |
| Сторінка досяжна через каталог, а не лише через sitemap | Тест внутрішніх посилань |

Виклики, що не пройшли критерії, лишаються в каталозі й запускаються, але отримують `noindex, follow` і не потрапляють у sitemap.

Публікація йде хвилями. Перша містить близько 30 викликів. Наступну запускаємо, коли щонайменше 70% попередньої потрапило в індекс. Це наш робочий поріг, а не вимога Google: він не дає масштабувати сторінки, які пошук не приймає.

### 6.3 Технічний мінімум

- Весь контент індексованих сторінок є в HTML від сервера.
- Унікальні `title` (до 60 символів) і `description` (до 155), один `h1`, абсолютний canonical, `lang="uk"`, `og:locale=uk_UA`, Open Graph, зображення 1200×630.
- `sitemap.xml` формується з БД із реальним `lastmod`.
- `robots.txt` залежить від середовища. `/workout` у ньому не закриваємо, інакше Google не побачить `noindex`. CSS і JS теж не закриваємо.
- Англійські шляхи не шкодять пошуку: за словами Google, ключові слова в URL майже не впливають на позиції. Назви в `BreadcrumbList` лишаються українською.
- Редиректи 301: `http` на `https`, `www` на основний домен, кінцевий слеш.
- Невідомі URL повертають справжній 404.
- JSON-LD: `WebSite`, `Organization` з `alternateName` «Селф Файтер», `BreadcrumbList`, `Article` для порад.
- Внутрішня перелінковка: футер, хлібні крихти, хаби, пов'язані сторінки. Кожна сторінка досяжна за три кліки.
- Друга мова додається префіксом `/en/...`. `hreflang` виводиться автоматично, коли мов більше однієї.
- `robots.txt` не блокує пошукових ботів AI-сервісів: відповіді таких сервісів є окремим каналом пошуку.
- Банер згоди займає невелику частину екрана й не веде на окрему сторінку, як і радить Google.

Розмітку `FAQPage` і `HowTo` не додаємо: Google більше не показує ці rich results. Блоки запитань на сторінках можуть лишатися для людей. Rich result для `SoftwareApplication` вимагає `aggregateRating` або `review`, а вигаданих оцінок не буде.

### 6.4 Швидкість

| Показник | Поріг |
| -------- | ----- |
| LCP | ≤ 2,5 с |
| INP | ≤ 200 мс |
| CLS | ≤ 0,1 |
| Lighthouse SEO | 100 |
| Lighthouse Performance, мобільний профіль | ≥ 90 |
| Lighthouse Accessibility | ≥ 95 |
| JS публічної сторінки | ≤ 15 KB gzip |
| Початковий JS гри | ≤ 150 KB gzip |

Як досягаємо:

- Публічні сторінки не завантажують React і скрипти Google, не запускають сесію й не залежать від cookie, тому їх можна кешувати на CDN.
- Шрифти лежать на нашому домені, а не на Google Fonts, як у макетах. Попередньо завантажуємо лише шрифт `h1`. `font-display: swap` і резервний шрифт із `size-adjust` прибирають зсув верстки.
- Хешовані файли мають `Cache-Control: immutable` і заздалегідь стиснуті Brotli-версії.
- Гра завантажується окремим бандлом і ділиться на частини за маршрутами. Усі частини попередньо завантажуються, тому розпочате тренування не залежить від мережі.

### 6.5 Запуск і контроль

- Підтвердити сайт у Search Console і Bing Webmaster Tools через DNS.
- Щотижня переглядати запити й покази, покращувати сторінки, що вже отримують покази.
- Отримати перші посилання: українські спільноти про спорт, Telegram-канали, каталоги, Product Hunt.

Новий домен зазвичай набирає позиції місяцями. Перших користувачів для перевірки §19 доведеться залучати напряму, а пошук працюватиме на довгу дистанцію.

### 6.6 Контроль у CI

Для кожного URL із `sitemap.xml` тести перевіряють: статус 200, один `h1`, унікальні `title` і `description`, canonical збігається з URL, JSON-LD коректний, `noindex` відсутній. Для `/workout` тест навпаки вимагає `noindex`. Перевірка після деплою гарантує, що production не закритий від індексації. Бюджети Lighthouse блокують merge.

Виклики перевіряються окремо: `generated.json` збігається з результатом генератора, кожна конфігурація проходить валідацію §11.5, а `app:content:lint` не знаходить майже однакових текстів серед індексованих сторінок.

## 7. CI/CD

Репозиторій уже на GitHub, тому використовуємо GitHub Actions.

**`ci.yml`** запускається на кожен PR і push у `main`:

| Завдання | Перевірки |
| -------- | --------- |
| backend | PHP CS Fixer, PHPStan, `composer audit`, `lint:twig`, `lint:container`, `doctrine:schema:validate`, PHPUnit на реальному MySQL |
| frontend | ESLint, `tsc --noEmit`, Vitest із порогами покриття, `npm audit --audit-level=high`, бюджет бандла, актуальність `generated.json` |
| image | hadolint, actionlint, збірка prod-образу, Trivy, запуск `compose.prod.yaml`, smoke-тест |
| e2e | Етап 6. Prod-образ із MySQL, Playwright на Mobile Chrome, Mobile Safari і Desktop, axe |
| seo | Етап 7. SEO-тести за sitemap, Lighthouse CI |

Завдання `frontend` запускає лише контейнер Node, тому не чекає на збірку PHP-образу.

**`deploy.yml`** просуває один і той самий образ середовищами:

| Подія | Результат |
| ----- | --------- |
| Merge у `main` | Образ `ghcr.io/iadmitrencko/self-fighter:<sha>` автоматично йде на staging |
| Git-тег `vX.Y.Z` | Той самий образ без перезбірки йде на production |
| Невдала перевірка після деплою | Автоматичний відкат до попереднього образу |

Послідовність на сервері через SSH:

1. `docker compose pull`
2. Міграції та `app:content:sync` в окремому контейнері
3. `docker compose up -d --wait`
4. Перевірка `/healthz`, `/` і `robots.txt`, за потреби відкат

Правила:

- Міграції сумісні з попередньою версією коду, інакше відкат небезпечний. API так само приймає запити від гри попередньої версії (розділ 3.7).
- Секрети, зокрема `GOOGLE_CLIENT_ID` і `GOOGLE_CLIENT_SECRET`, лежать у GitHub Environments і в `.env` на сервері, але не в Git.
- MySQL не публікується назовні.
- Дії GitHub закріплені за повним SHA, а інструменти запускаються з образів, закріплених за digest. Dependabot щомісяця пропонує оновлення дій.
- `aquasecurity/trivy-action` не використовуємо: у березні 2026 його теги були скомпрометовані (CVE-2026-33634). Trivy отримує лише архів образу, без Docker-сокета й токена.
- Образ збирається під архітектуру VPS. Локальна машина має arm64, тому dev-образ завжди будується локально.
- Перезапуск контейнера дає кілька секунд простою. Для MVP це прийнятно.

| Вимога §17.3 | Рівень | Інструмент |

| Вхід, об'єднання, черга надсилання | E2E | Playwright |

Справжній Google у тестах не викликаємо: вхід працює через підробленого постачальника OAuth.

Обов'язкові межові випадки:

- `M=1` на всіх рівнях, `M=90` на середньому дає 27–63, `M=100` відповідає таблиці §8.3.
- Ціль 10 і результати 9, 10, 11 за обома правилами (§6.5).
- Драбина: `max=1` із поверненням має один етап, `max=5` має дев'ять, провал на першому етапі дає максимальний пройдений етап 0.
- Подвійне підтвердження створює один запис.
- Перезавантаження під час бою не змінює значень суперника.
- Після видалення власної вправи історія й «Повторити» працюють зі знімка.
- Без згоди й після відмови сайт не надсилає жодної події.
- Кожен згенерований виклик проходить валідацію §11.5.
- Повторне об'єднання не створює дублікатів, а власні вправи з однаковою назвою зливаються.
- Спроба, завершена без мережі, надсилається один раз після відновлення зв'язку й не потрапляє до іншого користувача.
- Один користувач не може прочитати чи змінити дані іншого.
- Після видалення даних гостя чи облікового запису нічого не лишається, а події втрачають `user_id`.
- Публічні сторінки не встановлюють cookie.
- Перегляд сторінок і гри без жодного запису не створює гостя.
- Під час входу й виходу токен пристрою змінюється, а старий більше не діє.
- Перший вхід лишає дані гостя за тим самим `user_id`, а після виходу дані облікового запису недоступні.
- Поточна спроба іншої версії формату в буфері відкидається без збою гри.

## 9. Прогалини в дизайні

Усі сім файлів `design/*.dc.html` посилаються на `./support.js`, якого немає в репозиторії, тому прототипи не запускаються самостійно. Вони слугують еталоном структури, кольорів і логіки.

| Чого бракує | Рішення |
| ----------- | ------- |
| Налаштування «Випадкового суперника», «Рівнів» і «Драбини» | Збираємо зі спільних блоків `SetupTarget` |
| Форма власної вправи | Нижня панель на мобільному, діалог на десктопі |
| Екран бою для режиму «Ціль» | Блок цілі замість «Суперник зробив», рахунок «виграно : програно» |
| Повний результат драбини | У макеті лише «Повторити» й «Історія». Додаємо поля §13.1 і §13.3 та кнопку «Нове тренування» |
| Десктоп для екранів гри | Центрована колонка, ширша таблиця цілей |
| Таблиця цілей для багатьох вправ | Макет розрахований на 2 стовпці з 20 можливих. На мобільному від 4 вправ показуємо акордеон за вправами (§16.3) |
| Прогрес великих тренувань | Сітка сегментів не вміщає 400 етапів бою чи 199 етапів драбини. Бій переходить на суцільну смугу, драбина показує вікно навколо поточного етапу |
| Службові стани | Порожня історія, завантаження, помилка мережі, підтвердження переривання, відновлення спроби, 404 |
| Шаблони SEO-сторінок, каталог викликів | Будуємо на токенах лендінгу |
| Банер згоди | Невелика панель унизу екрана, кнопки однакової ваги |
| Верхній етап драбини за «Перевиконати» | Підказка «Зроби {max} або більше» замість «Зроби більше {max}» (R2) |
| Кнопка входу | За правилами Google: стандартний логотип, текст «Увійти через Google», темний варіант кольорів |
| Вхід і дані користувача | Пропозиція увійти на екрані результату й в історії, екран облікового запису з експортом і видаленням даних, діалог об'єднання, позначка «очікує надсилання» |
| Футер | Додаємо навігацію для перелінковки |
| Контраст номерів режимів | `#5E626A` на `#1B1D21` дає 2,76:1. Замінюємо на `#8A8D94` з палітри макетів, це 5,08:1 |
| Зміна кількості раундів | Макет відкидає значення при зменшенні. Зберігаємо їх до старту, щоб помилковий клік не стирав ручні цілі |
| «Перервати» | У макеті це пряме посилання. Додаємо підтвердження (R12) |

## 10. Ризики

| Ризик | Наслідок | Що робимо |
| ----- | -------- | --------- |
| Гість очищує cookie або відкриває сайт в іншому браузері | Історія лишається на сервері, але гість до неї вже не дістанеться, що б'є по §2 | Пропозиція увійти після першого тренування й на екрані історії, пояснення на екрані облікового запису |
| Сервер недоступний | Історія й власні вправи не відкриваються | Розпочате тренування триває, а результат чекає в черзі. Зовнішній моніторинг доступності й бекапи (етап 10) |
| Боти чи зловмисник масово створюють гостей | Зростає таблиця `user` і навантаження на базу | Гість з'являється лише під час першого запису, `/api` закритий у `robots.txt`, створення гостей обмежене за частотою, покинуті гості видаляються |
| Пошук дасть трафік лише за місяці | §19 не вдасться перевірити на органічних користувачах | Перших користувачів залучаємо напряму |
| Запити-гіпотези не мають попиту | Контент не приносить трафіку | Перевірка в Keyword Planner до написання текстів, щотижневий розбір Search Console |
| Більшість екранів не мають макета | Затягування етапу 6 | Спільні блоки, повторне використання токенів |
| Згенеровані виклики сприйняті як масовий контент | Google може знизити не лише ці сторінки, а й увесь сайт | Критерії з розділу 6.2, публікація хвилями, контроль індексації |
| Частина відвідувачів відхилить аналітику | Показники §19 занижені | Трактуємо цифри як нижню межу й доповнюємо розмовами |
| Вимоги до банера взяті з рекомендацій EDPB, а не з юридичного висновку | Текст може потребувати уточнення | Якщо частка аудиторії з ЄС стане помітною, перевіряємо текст у юриста |
| Вхід розширює обсяг першої версії | Запуск зсувається приблизно на тиждень, а перевірка гіпотези §1.2 починається пізніше | Етап 9 незалежний: якщо часу забракне, запускаємось без нього |
| Сервер зберігає історію тренувань усіх користувачів і персональні дані облікових записів | Витік або втрата зачіпає реальних людей | Мінімум даних, токени Google не зберігаємо, у базі лише хеші токенів пристроїв, ізоляція за `user_id`, шифровані бекапи, перевірка відновлення, видалення даних |
| Вбудовані браузери застосунків, наприклад Telegram чи Instagram, можуть блокувати вхід Google | Частина людей не зможе увійти | Підказка відкрити сайт у звичайному браузері, гра працює і без входу |

Щодо Safari: після 7 днів користування браузером без взаємодії із сайтом WebKit видаляє все, що записали скрипти: `localStorage`, IndexedDB і cookie з JavaScript. Cookie, який сервер поставив у відповіді HTTP, це правило не зачіпає, якщо його не ставить сторонній сервер, схований за CNAME чи чужою IP-адресою. Cookie пристрою ставить той самий сервер, що віддає сторінки, тому історія гостя від цього правила не залежить, а в `localStorage` лежить лише короткочасний буфер. Поведінку перевіряємо на реальному iPhone разом із §18 (етап 10).

## 11. Що потрібно від власника проєкту

1. Обрати й купити домен.
2. Надати VPS і SSH-доступ.
3. Надати доступ до Google-акаунта для Search Console і Keyword Planner.
4. Визначити автора або рецензента текстів.
5. Надати контакт для політики приватності, умов користування й сторінки про проєкт.
6. Налаштувати Google Cloud за кроками нижче.
7. Увімкнути захист гілки `main` за кроками нижче.

### Захист гілки `main`

Налаштування доступне після першого запуску CI, бо назви перевірок з'являються лише тоді.

1. На GitHub відкрити Settings → Rules → Rulesets → New ruleset → New branch ruleset.
2. Задати назву `main`, Enforcement status: Active, а в Target branches обрати Include default branch.
3. Увімкнути Require a pull request before merging.
4. Увімкнути Require status checks to pass і додати `backend`, `frontend`, `image`.

Після цього прямі push у `main` не працюватимуть: зміни потрапляють туди лише через pull request.

### Налаштування Google Cloud

Спеціальних дозволів і оплати не потрібно. Повна перевірка застосунку теж не потрібна, бо ми просимо лише `openid`, `email` і `profile`. Для локальної розробки домен не потрібен: вистачає проєкту для розробки з адресою `localhost`.

1. Увімкнути двоетапну перевірку в акаунті Google.
2. Підтвердити домен у Search Console тим самим акаунтом.
3. Створити два проєкти: один для розробки й staging, другий для production.
4. У Google Auth Platform → Branding заповнити назву Self-Fighter, email підтримки, посилання на головну, політику приватності й умови користування, а також авторизований домен.
5. В Audience обрати External і натиснути Publish app.
6. У Data access додати `openid`, `email`, `profile`.
7. У Clients створити клієнта типу Web application з адресою повернення:
   - розробка: `http://localhost:8080/connect/google/check`;
   - staging: `https://staging.{домен}/connect/google/check`;
   - production: `https://{домен}/connect/google/check`.
8. Зберегти Client ID і Client Secret одразу, бо секрет показується один раз. Вони йдуть у GitHub Secrets і `.env` на сервері, але не в Git і не в чат.
9. Після запуску подати застосунок на перевірку бренду. Без неї вхід працює, але Google показує лише домен. Після схвалення натиснути Publish branding протягом 7 днів.
