# Self-Fighter — план реалізації MVP

**Основа:** `PROJECT_SPECIFICATION.md` v1.3 і макети з `design/`.
**Дата:** 2026-10-30, оновлено 2026-11-10 (етап 11, гра «Козак»). Версії стеку та їх сумісність перевірені в реєстрах пакетів 2026-10-30.
**Оцінки:** орієнтовні, у робочих днях одного розробника.

## 1. Ключова ідея

Гра працює без реєстрації, а дані кожного користувача зберігаються в MySQL (§15). Гість теж є користувачем: браузер знаходить його за cookie пристрою. Необов'язковий вхід через Google додає до того самого користувача спосіб входу й відкриває його дані на інших пристроях (§23). Реєстрацію за email і паролем додамо пізніше як ще один спосіб входу.

| Шар | Технологія | Відповідальність |
| --- | ---------- | ---------------- |
| Публічні сторінки | Symfony + Twig | Лендінг, контент, готові виклики |
| Гра | React + TypeScript | Екрани тренування та правила режимів |
| Дані користувачів | MySQL через API | Вправи, історія й налаштування гостей і облікових записів |
| Буфер у браузері | `localStorage` | Поточна спроба й завершені спроби, що чекають надсилання |
| Серверні дані | MySQL | Каталог, контент, події |

Наслідки:

- Правила гри існують лише в TypeScript, дублювання в PHP немає.
- Формат даних змінюють міграції на сервері. Браузер не зберігає даних, які довелося б мігрувати після релізу.
- Екрани гри працюють із контрактом сховища й не знають, як влаштоване API (розділ 3.7).
- Індексовані сторінки не залежать від виконання JavaScript, не запускають сесію й не читають cookie.
- Розпочате тренування не потребує сервера.

### 2.2 Закриті прогалини специфікації

| # | Прогалина | Рішення |
| --- | --------- | ------- |
| R6 | §6.6 і §12.3 згадують нічию у вправі, а правила §6.5 і §7.4 її не передбачають. | Вправа має два результати: перемога або поразка. Рівний результат за «Перевиконати» є поразкою, як і в макетах. Підрахунок раунду все одно ігнорує нічию, тож §6.6 виконується. |
| R7 | §8.4 вимагає валідний діапазон, але `M=1` дає 1–0 на простому й середньому рівнях. | `hi = max(lo, hi)`, тобто 1–1. |
| R8 | Спосіб округлення відсотків. | Лише цілочисельно: `ceil(M * pct / 100)`. Вираз `M * 0.7` при `M=90` дає 62 замість 63. |
| R9 | §8.5 не задає ймовірність і розмір перевищення. | Імовірність 10%. Значення рівномірне в межах `[M+1, max(M+1, ceil(M*120/100))]`. Константи лежать у `domain/config/limits.ts`. |
| R10 | Немає числових лімітів (§4.3, §9.2). | Драбина: максимум 100 (199 етапів із поверненням). Ціль і результат: до 9999. |
| R11 | Вимоги до вправи (§5.2). | Назва до 60 символів без повторів у каталозі (без урахування регістру). Опис до 200 символів. |
| R12 | §12.1 згадує «завершити або перервати». | Дострокова дія одна, з підтвердженням: у бою гри це «Відступити», і відступ зараховує поразку (§24.6). Завершення настає автоматично після останнього етапу. |
| R13 | Межі `make down` і `make kill`. | `down` виконує `docker compose stop`. `kill` видаляє контейнери й образи, а volume MySQL лишає, бо про дані в завданні не йшлося. |
| R18 | §6.4 не уточнює, чи «Заповнити всі» перезаписує ручні значення. | Перезаписує всі раунди значенням першого й скидає ручні позначки, як у макеті `SetupTarget`: це явна дія користувача. Автоматичне копіювання першого раунду ручних значень не чіпає. |
| R19 | §6.4 не описує очищену ручну клітинку. | Вона знову стає автоматичною: значення користувача в ній більше немає, тож руйнувати нічого. |
| R20 | За правилом «Перевиконати» ціль 9999 недосяжна, бо результат обмежений тим самим числом. | Не обмежуємо: випадок нереальний, а гра лишається коректною і зараховує поразку у вправі. |

## 3. Архітектура

### 3.1 Схема

```text
Браузер
├── Публічні сторінки (HTML із Twig, мінімум JS)
└── Гра (React) ──── localStorage: поточна спроба, черга надсилання
        │
        │ сторінки, події, API даних користувача
        ▼
Cloudflare (DNS, CDN)
        ▼
app: FrankenPHP + Symfony ──── MySQL
        │
        └── Google OAuth (лише під час входу)
```

### 3.2 Стек

Версії фіксуються в `composer.lock`, `package-lock.json` і тегах образів.

| Компонент | Вибір | Примітка |
| --------- | ----- | -------- |

| Користувачі | Symfony Security, власний автентифікатор за cookie пристрою | Той самий механізм для гостя й облікового запису, API без сесії PHP |

Хостинг за замовчуванням: один VPS (2 vCPU, 4 GB RAM) із Docker і Cloudflare перед ним. Прив'язки до провайдера немає.

Шари `frontend/src` відповідають §17.1. `domain/` не імпортує React, сховище й тексти (ESLint) і не бачить браузерних API (`tsconfig.domain.json` не підключає DOM). Обидві перевірки входять у `make lint`, тож працюють у CI.

Бекенд розкладено на модулі за bounded contexts: `Account` (користувачі, пристрої, вхід), `Workout` (спроби, власні вправи, налаштування), `Content` (контент сайту й готові виклики, етап 7), `Analytics` (події §19, етап 8), `Site` (Twig-сторінки) і спільне ядро `Shared`.

| Шар | Вміст | Залежить від |
| --- | ----- | ------------ |
| `Domain` | Сутності, value objects, інтерфейси репозиторіїв | Лише `Shared/Domain` |
| `Application` | Сценарії й порти | `Domain`, порти `Shared`, PSR |
| `Infrastructure` | Doctrine з XML-мапінгом, JSON Schema | Будь-що, крім `Presentation` |
| `Presentation` | Контролери, автентифікатор, консольні команди | `Application`, `Domain`, Symfony |

Модулі не бачать один одного: дані іншого модуля вони знають лише за id, а спільні дії, як-от експорт і видалення даних користувача, йдуть через порти `Shared`. Межі перевіряє Deptrac у `make lint`.

### 3.4 Маршрути

Шляхи й слаги англійською, без кінцевого слеша: `/guides/ladder-training`, `/game/journey/forest-ravens/1`. Заголовки й текст сторінок лишаються українською. Слаги режимів: `target`, `random-opponent`, `opponent-levels`, `ladder`.

| URL | Рендер | Індексація |
| --- | ------ | ---------- |
| `/` | Twig | index |
| `/guides`, `/guides/{slug}` | Twig | За критеріями якості (§21.4) |
| `/challenges`, `/modes`, `/exercises` і вкладені, `/workout/challenge/{slug}` | Symfony | Переадресація в гру: розділи прибрано (§21.3) |
| `/about`, `/privacy`, `/terms` | Twig | index |
| `/workout` і вкладені маршрути | Symfony | Переадресація на ті самі екрани бою гри: розділ прибрано (§24.1) |
| `/game` і вкладені маршрути (§24) | Twig-оболонка + React | `noindex, follow` |
| `/sitemap.xml`, `/robots.txt` | Symfony | не застосовується |
| `/api/v1/*` | JSON | заборонено в `robots.txt` |
| `/connect/google`, `/connect/google/check` | Symfony | заборонено в `robots.txt` |
| `/healthz` | Текст | не застосовується |

Окремого розділу тренувань `/workout` більше немає: усі тренування відбуваються в бою гри «Козак». Його адреси `/workout`, `/workout/setup/{mode}`, `/workout/fight`, `/workout/result/{id}`, `/workout/history` і `/workout/account` переадресовують на `/game/fight`, `/game/fight/setup/{mode}`, `/game/fight`, `/game/fight/result/{id}`, `/game/history` і `/game/settings` разом із рядком запиту, тож старі посилання й вхід через Google, розпочатий там, ведуть туди. Інші адреси під `/workout` дають 404.

Маршрути гри «Козак» (§24): `/game`, `/game/ranks`, `/game/history`, `/game/settings`, `/game/fight`, `/game/fight/setup/{mode}`, `/game/fight/battle`, `/game/fight/result/{id}`, `/game/journey`, `/game/journey/{campaign}`, `/game/journey/{campaign}/{stage}`, `/game/journey/{campaign}/{stage}/{level}`, `/game/journey/battle`, `/game/journey/result/{id}`. Symfony знає їх поіменно, тому невідомий шлях повертає справжній 404, а не оболонку зі статусом 200. Він перевіряє slug кампанії й числа етапу та рівня, а неіснуючий рівень відомої кампанії показує екран «Тут нічого немає».

### 3.5 Дані

**MySQL**

| Таблиця | Вміст |
| ------- | ----- |
| `exercise` | Slug, назва, ознака наявності в грі, порядок, SEO-поля, HTML сторінки вправи |
| `content_page` | Тип (режим, порада, службова), slug, SEO-поля, HTML, дати |
| `challenge` | Slug, конфігурація гри, вправи, рівень, обчислені дані, SEO-поля, HTML, ознака індексації, дати |
| `analytics_event` | Назва, режим, результат, код помилки налаштування, час, `user_id`, якщо користувач уже є |
| `user` | Дата створення, а в облікового запису ще ім'я й підтверджений email від Google. Фото не зберігаємо: картинка з серверів Google показувала б Google кожен перегляд |
| `user_identity` | Користувач, спосіб входу (`google`, пізніше `email`), зовнішній ідентифікатор (`sub` для Google), дата |
| `device` | Хеш токена з cookie пристрою, поточний користувач браузера, гість, до якого браузер повертається після виходу, дати |
| `attempt` | Ідентифікатор спроби, користувач, режим, результат, slug готового виклику, дата завершення, `schemaVersion`, JSON із деталями; індекси за користувачем, режимом, результатом і датою (§14.3). Для гри «Козак» ще пул енергії бою, рівень походу й момент, коли пул знову повний (§24) |
| `custom_exercise` | Ідентифікатор, користувач, назва, опис, дати |
| `workout_settings` | Користувач і останні конфігурації всіх режимів одним JSON |

Таблиці різних модулів пов'язує лише значення `user_id`, зовнішніх ключів між ними немає. Тому видалення користувача проходить через кожен модуль (розділ 3.7).

Контент живе в Git (`backend/content/`), а команда `app:content:sync` переносить його в MySQL під час деплою. Адмінки немає: це менше коду й менша поверхня атаки. Готові вправи й конфігурацію відкритого виклику Symfony вбудовує в оболонку гри як JSON, тому окремого API для них немає. Дані користувача гра отримує через API (розділ 3.7).

**Буфер у браузері**

| Ключ `localStorage` | Вміст |
| ------------------- | ----- |
| `self-fighter:active-session` | Поточна спроба для відновлення після перезавантаження |
| `self-fighter:game-session:fight`, `self-fighter:game-session:campaign` | Поточний бій і поточний рівень походу гри «Козак», окремо від тренування сайту (§24) |
| `self-fighter:outbox:{id}` | Завершена спроба з власником, що чекає надсилання. Кожна спроба має свій ключ, тож вкладки не перезаписують одна одну |

Буфер не є сховищем: запис лежить у ньому, доки триває тренування або доки не повернеться зв'язок. Тому браузер його не мігрує. Поточна спроба іншої версії формату відкидається, бо незавершені спроби не зараховуються (§12.4), а спроби з черги сервер приймає як є (розділ 3.7).

Гарантії, закладені в модель:

- Завершена спроба незмінна: API лише додає спроби. Повторний `PUT` із тим самим вмістом нічого не змінює, а інший вміст за тим самим ідентифікатором отримує 409 (§17.2).
- Ідентифікатор спроби (UUID v7) створюється на клієнті під час старту, тому повторне збереження не дублює запис.
- Статистика не зберігається окремо, а щоразу обчислюється зі спроб. Сума перемог, нічиїх і поразок завжди збігається з історією (§14.2).
- Кожен запис містить `schemaVersion`, а час зберігається в UTC.

### 3.6 Ігровий рушій

```ts
// Фіксує конфігурацію, id, час старту і всі значення суперника
createSession(config, { rng, now, newId }): Session

// Індекс поточного етапу або null, якщо спроба завершена
nextStageIndex(session): number | null

// Повторний виклик для заповненого етапу нічого не змінює
submitResult(session, stageIndex, reps): Session

// Створює незмінний запис для історії
finalize(session, finishedAt): Attempt

passesTarget(actual, target, rule)              // over: >, meet: >=
ladderStageRule(target, max, rule)              // верхній етап: meet (R2)
```

Значення суперника генеруються наперед і зберігаються в сесії поточного бою (`gameSessions.fight`), тому перезавантаження не змінює вже показаний результат (§7.3). Захист від подвійного натискання працює в рушії, а не лише в кнопці (§12.2). RNG, час і генератор id передаються ззовні, що робить тести детермінованими.

Кожен етап зберігає правило, яке до нього застосовується. Тому R2 живе в одному місці, а підказка на екрані й підрахунок результату не потребують окремої умови для верхнього етапу драбини. `computeFightResult` враховує лише завершені раунди, тож дає і підсумок бою, і рахунок під час гри.

### 3.7 Користувачі й дані

Кожен, хто щось зберіг, є користувачем із `user_id`. Гість відрізняється від облікового запису лише тим, звідки можна дістатися до його даних.

| Користувач | Ідентифікатор | Звідки доступні дані |
| ---------- | ------------- | -------------------- |
| Гість | Токен пристрою в cookie | Лише з цього браузера |
| Вхід через Google | `sub` облікового запису Google | З будь-якого пристрою після входу |
| Вхід через email, пізніше | Підтверджений email | З будь-якого пристрою після входу |

Google знаходимо за `sub`, а не за email: так радить сам Google, бо email облікового запису Google може змінитися. Email у `user` зв'язує вхід через Google з майбутнім входом через email, тож той самий підтверджений адрес не створить другого облікового запису (§23.4).

Cookie пристрою:

- Містить випадковий токен на 256 біт. У MySQL лежить лише його SHA-256, тому витік бази не дає змоги увійти від імені користувача.
- Має `HttpOnly`, `Secure`, `SameSite=Lax` і префікс `__Host-`. Скрипти його не бачать, тож XSS не вкраде токен.
- Живе 400 днів, це максимум Chrome. Сервер продовжує його під час активності, але не частіше разу на добу.
- Сервер ставить його у відповіді HTTP, тому Safari не стирає його через 7 днів без відвідувань, як `localStorage`, IndexedDB і cookie зі скриптів (розділ 10).
- Окремої сесії входу немає: після входу той самий cookie веде до облікового запису.
- Під час входу й виходу токен замінюється новим, тому заздалегідь підкинутий токен не дасть доступу до облікового запису.

Користувачі:

- Гість з'являється під час першого запису через `POST /api/v1/me`, а не під час відвідування. Боти й люди, які лише дивляться, записів не створюють, а створення гостей обмежене за частотою.
- `GET /api/v1/me` повертає поточного користувача, тому HTML оболонки не залежить від користувача. Вправи й налаштування віддає модуль Workout окремими запитами, і браузер кешує кожен ресурс.
- Гостя, який не користувався застосунком 400 днів, видаляє щоденна команда: його cookie на той час уже не діє.

Вхід:

- Symfony веде користувача на Google через серверний потік Authorization Code зі `state` і PKCE. Запитуємо лише `openid`, `email`, `profile`. `state` і PKCE на час входу лежать у сесії Symfony, яку запускають лише маршрути `/connect/*`. Токени Google не зберігаємо.
- Якщо цей обліковий запис Google ще не використовувався, він додається до гостя цього браузера, а без гостя створюється новий користувач. Гість стає обліковим записом, і дані нікуди не переносяться.
- Якщо обліковий запис Google уже належить іншому користувачу, а гість має спроби чи власні вправи, гра пропонує їх об'єднати (§23.3). До рішення гість лишається в `device` поруч з обліковим записом, а `GET /api/v1/me` повертає його полем `guest` разом із кількістю спроб і вправ. `POST /api/v1/me/merge` об'єднує однією транзакцією: спроби змінюють власника, вправи з однаковою назвою зливаються, налаштування облікового запису мають пріоритет, події аналітики переходять до облікового запису. Після відмови дані лишаються в гостя цього браузера. Гість без таких даних приєднується одразу, без питання.
- `POST /api/v1/me/logout` повертає браузер до його гостя, якщо такий лишився, або до стану без користувача.
- Видалення облікового запису повертає кожен браузер, де він був відкритий поруч із гостем, до цього гостя, тож чужі дані не зникають разом з обліковим записом.

Дані:

- Екрани працюють лише з асинхронним контрактом `ExerciseStore`, `AttemptStore`, `SettingsStore`. Робоча реалізація звертається до API, а реалізація в пам'яті потрібна для тестів екранів.
- Завершена спроба спершу потрапляє в чергу браузера, а потім надсилається ідемпотентним `PUT /api/v1/attempts/{id}`. Без мережі вона чекає й надсилається пізніше (§15.4). Запис у черзі прив'язаний до `user_id`, тому не потрапить до іншого користувача.
- Формат спроби описує одна JSON Schema в репозиторії. Vitest перевіряє, що кожна спроба з `domain/` їй відповідає, а PHP перевіряє за нею запити. Зміна формату означає нову `schemaVersion` і міграцію Doctrine для наявних записів.
- API приймає записи поточної й попередньої версії формату, тому ні вкладка, відкрита до деплою, ні черга, що чекала мережі, не втрачають даних.
- Правила гри лишаються на клієнті, а сервер перевіряє лише структуру, межі й власника даних. Рейтингів немає, а результат користувач і так вводить сам.
- Змінювальні запити захищені від CSRF: `SameSite=Lax` і перевірка заголовка `Origin`.
- Кожен користувач, зокрема гість, може завантажити свої дані й видалити їх (§15.5). Кожен модуль, що зберігає дані користувачів, реалізує порт `UserDataHolder`, тож експорт і видалення збирають частини з усіх модулів. Аналітика під час видалення лишає події, але прибирає з них `user_id`.

| Правило | Навіщо |
| ------- | ------ |
| `list()` приймає фільтри й курсор, `stats()` є окремим методом | Сервер не віддає всю історію, статистику рахує SQL |
| Ідентифікатори спроб і власних вправ створюються на клієнті | Повторне надсилання й об'єднання не створюють дублікатів (§17.2) |
| Спроба є самодостатнім JSON із `schemaVersion` | Той самий формат лежить у черзі браузера й у MySQL, а міграція знає версію кожного запису |
| Публічні сторінки не запускають сесію й не читають cookie | Користувачі не погіршують кешування і швидкість SEO-сторінок |
| Користувач, спосіб входу й браузер зберігаються окремо (`user`, `user_identity`, `device`) | Email і пароль додаються пізніше без переробок |

## 4. Docker і Makefile

Для роботи над проєктом на машині потрібен лише Docker. PHP, Composer і Node на хості не використовуються.

| Команда | Дія |
| ------- | --- |
| `make up` | Створює `.env` із `.env.example`, якщо його немає. Виконує `docker compose up -d --build --wait`, встановлює залежності, застосовує міграції, синхронізує контент і друкує адресу |
| `make down` | `docker compose stop`: контейнери й дані лишаються |
| `make kill` | `docker compose down --rmi all --remove-orphans`: видаляє контейнери, мережу та образи проєкту, volume MySQL лишається |

Допоміжні цілі: `help`, `logs`, `ps`, `sh`, `test`, `lint`, `fix`, `migrate`, `metrics`. CI викликає ті самі `make test` і `make lint`, тому локальна перевірка відповідає CI.

Правила:

- `make up` на чистому клоні доводить проєкт до робочого стану без ручних кроків.
- `name: self-fighter` у `compose.yaml` обмежує `make kill` цим проєктом. `docker system prune` не використовуємо.
- Dev-адреси: застосунок `http://localhost:8080`, Vite на порту 5173, MySQL на `127.0.0.1:3307`. Порт 3306 на машині розробки зайнятий іншим проєктом. Порти змінюються через `.env`.
- `vendor/` і `node_modules/` доступні на хості для PhpStorm, але встановлюються лише в контейнерах. `var/` лежить у volume заради швидкодії на macOS.
- Prod-образ збирається багатостадійно: Node будує фронтенд, а фінальна стадія містить код, залежності без dev-пакетів, `public/build` і прогрітий кеш.
- Контейнери `app` і `mysql` мають healthcheck, на який спирається `--wait`.

### Етап 8. Згода й аналітика

**Статус:** виконано 2026-11-03.

- **Банер.** Twig рендерить його в рамці кожної сторінки, разом із грою, а показує `src/consent/consent.ts` без React і лише тому, хто ще не вирішив. Це невелика панель унизу вікна з однаковими кнопками «Дозволити» й «Відхилити». Сторінка стає довшою на висоту банера, тож її кінець не ховається під ним. Банер чекає на шрифти: з резервним шрифтом він виріс би після їх завантаження й зсунув сторінку.
- **Рішення.** Воно лежить у `localStorage` цього браузера. Кнопка «Згода на аналітику» у футері відкриває банер знову. Перед кожною подією гра перевіряє згоду, тож зміна рішення діє одразу.
- **Події.** Гра шле чотири події §19: старт кожного тренування, завершення з підсумком, повтор і код помилки налаштування, через яку старт не відбувся. Збій надсилання гру не зачіпає. Екрани звертаються лише до контракту `src/analytics/events.ts`, до реалізації ESLint їх не пускає.
- **Сервер.** `POST /api/v1/events` приймає тільки поля з `backend/schema/event.schema.json`, той самий файл перевіряє Vitest. Час сервер ставить сам, а користувача бере з cookie пристрою. Подія не створює гостя: у відвідувача без жодного збереження вона лишається без `user_id`. Старт іде після збереження налаштувань, які роблять нового гравця гостем, тож подія першого тренування вже знає користувача. Модуль Analytics бере участь в експорті даних, а під час видалення прибирає `user_id` зі своїх подій.
- **Команди.** `app:metrics:report` (`make metrics`) рахує показники SQL-запитами для гравців, чиє перше тренування припало на період. Дні рахуються за UTC. `app:events:purge` видаляє події, старші за 12 місяців.
- **Приватність.** Сторінка «Приватність» поки чернетка з `reviewed: false`: остаточний текст і контакт з'являться на етапі 10.
- **Перевірка.** E2E підтверджує, що без згоди й після відмови браузер не надсилає жодної події, а після дозволу події доходять до сервера разом із користувачем.

- Реалізувати банер згоди за §22. HTML рендерить Twig, логіка працює без React, тому банер є на всіх сторінках.
- Додати у футер посилання для зміни рішення.
- Реалізувати `POST /api/v1/events`: перелік дозволених полів, обмеження частоти. `user_id` береться з cookie пристрою, а не з даних клієнта.
- Реалізувати в модулі Analytics порт `UserDataHolder`: видалення даних користувача прибирає `user_id` з його подій.
- Надсилати події лише після згоди. Збій надсилання не впливає на гру.
- Реалізувати `app:metrics:report` і видалення подій, старших за 12 місяців.

| Показник §19 | Джерело |
| ------------ | ------- |
| Почали перше тренування | Користувачі з `workout_started` |
| Завершили перше тренування | Користувачі з `workout_completed` |
| Популярність режимів | `workout_started`, групування за `mode` |
| Повторні запуски | `workout_repeated` |
| Повернення через кілька днів | Користувачі з `workout_started` у різні дні |
| Труднощі налаштування | `setup_error` з кодом помилки, решта з розмов |
| Чи цікаво користувачам | Лише розмови |

Показники рахуються за `user_id`, тому гість, що очистив браузер, рахується як новий користувач. Цифри охоплюють лише відвідувачів, які дали згоду. Для малої вибірки §19 така точність достатня.

**Готово, коли** без згоди сайт не надсилає жодної події, а кількісні показники §19 можна отримати однією командою.

### Етап 9. Вхід через Google

**Статус:** виконано. Код готовий 2026-11-04, а 2026-11-06 вхід перевірено зі справжнім Google на клієнті розробки. Клієнта production створюємо на етапі 10. Без клієнта гра ховає кнопку входу. Вхід іде серверним потоком Authorization Code із `state` і PKCE через `/connect/google`: сесію Symfony запускають лише ці адреси, а відповідь Google її закінчує. Сервер бере `sub`, ім'я й підтверджений email з ID-токена, який отримує прямо від Google в обмін на секрет клієнта, і не зберігає ні токенів Google, ні фото. Вхід і вихід замінюють токен пристрою, тож підкинутий заздалегідь токен нічого не відкриває. Перший вхід додає спосіб входу до гостя, а гість із даними поруч із наявним обліковим записом чекає рішення: діалог об'єднання після повернення від Google або картка на екрані «Мої дані». Об'єднання проходить через порт `UserDataHolder`, який отримав `summary()` і `transfer()`. Спроби з черги браузера йдуть лише своєму власнику: після входу гість передає їх обліковому запису, а після виходу спроби облікового запису чекають, доки він знову увійде в цьому браузері. Пропозицію увійти показують на екрані історії й після першого тренування, а у вбудованих браузерах застосунків гра підказує відкрити сайт у Safari чи Chrome. `app:guests:purge` не чіпає облікових записів і гостей, яких браузер тримає поруч з обліковим записом. Сторінка «Приватність» отримала чернетку розділу про вхід. `make e2e` проходить сценарії входу на двох пристроях, об'єднання, відмову й скасування з підробленим Google.

Сервер:

- Створити таблицю `user_identity` і додати в `device` гостя браузера, до якого повертає вихід.
- Реалізувати вхід через Google і вихід (розділ 3.7): прив'язку Google до гостя, пошук за `sub`, заміну токена пристрою.
- Реалізувати об'єднання гостя з наявним обліковим записом однією транзакцією.
- Навчити `app:guests:purge` пропускати користувачів зі способом входу. Раніше команда видаляла кожного, до кого не веде жоден браузер.

Гра:

- Додати кнопку входу, пропозицію увійти, вхід і вихід на екрані облікового запису, діалог об'єднання.
- Попереджати перед виходом про ненадіслані спроби (§15.4).
- Додати підказку для вбудованих браузерів.

**Готово, коли** історія видна на другому пристрої, перший вхід лишає дані гостя на місці, повторне об'єднання не створює дублікатів, а після виходу дані облікового запису в цьому браузері недоступні.

### Етап 11. Гра «Козак»

**Статус:** код виконано 2026-11-10. Розділ «Гра» (§24) живе під `/game`, у рамці сайту, з пунктом меню на кожному екрані. Лишилося вичитати сюжет, замінити ілюстрації-заглушки малюнками й наповнити кампанії «Чорний прапор» і «Степові вовки» та фінальну битву.

- звання й вигляд козака;
- слава;
- два пули енергії;
- похід «Січ» з усіма 61 рівнем «Лісових круків»;

Тести домену звіряють суми повторень кожного рівня з брифом, а покриття `domain/` лишається 100%.

**Дані.** Окремого сховища в гри немає: її бої — це спроби історії формату версії 3.

- Спроба гри має поле `game` з пулом енергії й моментом, коли пул знову повний. Рівень походу є новим режимом `campaign`.

- Слава, звання й прогрес обчислюються в браузері з цього звіту разом зі спробами, що чекають надсилання.
- Без мережі гра бере те, що сервер сказав востаннє, тож бій починається й закінчується офлайн. Гість, створений щойно, на сервері ще порожній, тож його звіт відомий і без запиту: перший бій нового гравця теж закінчується без мережі.
- Сервер приймає версії 2 і 3, а версію 1 більше не приймає. Міграція перевела наявні записи на версію 3 як тренування сайту.

**Екрани.**

- Вхід Vite `kozak` має власний бюджет 150 KB.
- «Козак» і «Звання» зроблено за `resesign/kozak.html` і `resesign/zvannya.html`. На «Козаку» є портрет, слава з кнопкою «?», енергії, переходи до бою й походу та бойовий рахунок. «Звання» показує всі звання за групами вигляду й поступ до наступного. На телефоні поступ стоїть над переліком, щоб не гортати 20 звань.
- «Історія» — п'ятий підрозділ гри, окремого макета для неї немає, тож вона зібрана з карток «Звань». Це та сама єдина історія §14: бої гри, рівні походу й старі тренування сайту разом зі статистикою, фільтрами за режимом (зокрема «Похід») і результатом та пропозицією увійти. Рівень відкривається у своєму результаті, а бій і старе тренування сайту — у результаті бою `/game/fight/result/{id}`. Google повертає браузер і на екрани гри, тож гра теж показує діалог об'єднання.
- «Налаштування» — шостий підрозділ, колишні «Мої дані» з `/workout/account`: вхід і вихід, перенесення даних браузера, завантаження й видалення. Шість вкладок не вміщаються на телефоні, тож вони гортаються вбік, а відкрита сама стає видимою.
- «Бій» показує ті самі екрани тренування через контекст арени (`src/app/arena.tsx`). Арена задає адреси, сховище поточної спроби, витрату енергії на старті й ноту слави на результаті.
- Кнопка «Почати тренування» в шапці, футері, на головній, у порадах і на сторінці 404 веде у вибір бою `/game/fight`, а «Гра» в шапці — до козака.
- Тренування відбуваються лише в грі: розділ `/workout` прибрано разом із входом Vite `app`. Контекст арени (`src/app/arena.tsx`) тепер задає лише бій гри, тож вихід посеред тренування завжди зараховує поразку. Незавершене тренування сайту, що лишилося в браузері, гра стирає при відкритті.
- Відступ посеред бою гри зараховується поразкою, щоб енергію не можна було повернути, покинувши невигідний бій.
- Похід зроблено за `kozak_design`. Бій рівня займає весь екран у модальному діалозі й не дає екрану згаснути (Wake Lock).
- Карти етапів 2–10 зібрано з елементів макета першого етапу.
- Назви кампаній, етапів і рівнів лежать у `src/i18n/kozak-names.ts` окремо від сюжету в `kozak.ts`.

**Перевірка:**

- Vitest проходить сторінки козака, звань, історії й налаштувань, хаб, карти, підготовку, бій, перемогу над рівнем і над босом, проходження кампанії, відступ і брак енергії.
- PHPUnit перевіряє формат версії 3, звіт гри, маршрути `/game`, переадресацію старих адрес історії й «Моїх даних» і повернення від Google на екрани гри.
- `make e2e` проходить перший рівень, відступ і бій гри з axe на трьох профілях, а також сторінки звань, історії й налаштувань і панель «Як здобути славу». Сценарії історії, даних і входу через Google тепер ідуть через `/game/history` і `/game/settings`.

**Готово, коли** перший похід можна пройти від першого рівня до Гнізда Чорного Крука на телефоні й на десктопі, а слава, звання й енергія збігаються з історією.

## 6. SEO

Технічне SEO лише дає сторінкам змогу потрапити в індекс. Трафік приносять сторінки, що відповідають на запити, які люди вже вводять.

### 6.1 Контент

Назву Self-Fighter поки ніхто не шукає, тому ставка йде на небрендові запити. Приклади нижче є гіпотезами: обсяги пошуку ще не перевірені. Перший крок етапу 7 — звірити їх у Keyword Planner і скоригувати список.

| Тип | Приклади сторінок | Роль |
| --- | ----------------- | ---- |
| Поради | «Як змусити себе тренуватися», «Що таке тренування драбиною» | Інформаційні запити й внутрішні посилання |

Спершу ставка була на готові виклики та сторінки вправ і режимів. Специфікація 1.7 їх прибрала: усе робиться під гру (§24.1), а пошуку лишилися поради й службові сторінки. Кожна порада веде в гру.

Авторські тексти мають бути оригінальними й вичитаними людиною. Тема здоров'я підвищує вимоги до довіри: потрібні автор, сторінка про проєкт, застереження щодо навантажень і посилання на джерела.

### 6.2 Генератор готових викликів

Прибрано разом із викликами (специфікація 1.7, §21.3): матриця, `generated.json`, генератор у `frontend/scripts` і `make challenges`. Готові вправи гри лишилися в `backend/content/exercises.yaml`.

### 6.3 Технічний мінімум

- Весь контент індексованих сторінок є в HTML від сервера.
- Унікальні `title` (до 60 символів) і `description` (до 155), один `h1`, абсолютний canonical, `lang="uk"`, `og:locale=uk_UA`, Open Graph, зображення 1200×630.
- `sitemap.xml` формується з БД із реальним `lastmod`.
- `robots.txt` залежить від середовища. Гру `/game` у ньому не закриваємо, інакше Google не побачить `noindex`. CSS і JS теж не закриваємо.
- Англійські шляхи не шкодять пошуку: за словами Google, ключові слова в URL майже не впливають на позиції. Назви в `BreadcrumbList` лишаються українською.
- Редиректи 301: `http` на `https`, `www` на основний домен, кінцевий слеш.
- Невідомі URL повертають справжній 404.
- JSON-LD: `WebSite`, `Organization` з `alternateName` «Селф Файтер», `BreadcrumbList`, `Article` для порад.
- Внутрішня перелінковка: футер, хлібні крихти, хаби, пов'язані сторінки. Кожна сторінка досяжна за три кліки.
- Друга мова додається префіксом `/en/...`. `hreflang` виводиться автоматично, коли мов більше однієї.
- `robots.txt` не блокує пошукових ботів AI-сервісів: відповіді таких сервісів є окремим каналом пошуку.
- Банер згоди займає невелику частину екрана й не веде на окрему сторінку, як і радить Google.

Розмітку `FAQPage` і `HowTo` не додаємо: Google більше не показує ці rich results. Блоки запитань на сторінках можуть лишатися для людей. Rich result для `SoftwareApplication` вимагає `aggregateRating` або `review`, а вигаданих оцінок не буде.

### 6.4 Швидкість

| Показник | Поріг |
| -------- | ----- |
| LCP | ≤ 2,5 с |
| INP | ≤ 200 мс |
| CLS | ≤ 0,1 |
| Lighthouse SEO | 100 |
| Lighthouse Performance, мобільний профіль | ≥ 90 |
| Lighthouse Accessibility | ≥ 95 |
| JS публічної сторінки | ≤ 15 KB gzip |
| Початковий JS гри «Козак» | ≤ 150 KB gzip |

Як досягаємо:

- Публічні сторінки не завантажують React і скрипти Google, не запускають сесію й не залежать від cookie, тому їх можна кешувати на CDN.
- Шрифти лежать на нашому домені, а не на Google Fonts, як у макетах. Попередньо завантажуємо лише шрифт `h1`. `font-display: swap` і резервний шрифт із `size-adjust` прибирають зсув верстки.
- Хешовані файли мають `Cache-Control: immutable`, а Caddy стискає відповіді Brotli на льоту. Заздалегідь стиснуті версії додамо, якщо стиснення почне помітно навантажувати сервер.
- Гра завантажується окремим бандлом. Поки він укладається в бюджет, на частини за маршрутами його не ділимо: увесь код гри вже в браузері, тож розпочате тренування не залежить від мережі.

### 6.5 Запуск і контроль

- Підтвердити сайт у Search Console і Bing Webmaster Tools через DNS.
- Щотижня переглядати запити й покази, покращувати сторінки, що вже отримують покази.
- Отримати перші посилання: українські спільноти про спорт, Telegram-канали, каталоги, Product Hunt.

Новий домен зазвичай набирає позиції місяцями. Перших користувачів для перевірки §19 доведеться залучати напряму, а пошук працюватиме на довгу дистанцію.

### 6.6 Контроль у CI

Для кожного URL із `sitemap.xml` тести перевіряють: статус 200, один `h1`, унікальні `title` і `description`, canonical збігається з URL, JSON-LD коректний, `noindex` відсутній. Для гри `/game` тест навпаки вимагає `noindex`. Перевірка після деплою гарантує, що production не закритий від індексації. Бюджети Lighthouse блокують merge. `app:content:lint` не знаходить майже однакових текстів серед сторінок.

## 7. CI/CD

Репозиторій уже на GitHub, тому використовуємо GitHub Actions.

**`ci.yml`** запускається на кожен PR і push у `main`:

| Завдання | Перевірки |
| -------- | --------- |
| backend | PHP CS Fixer, PHPStan, Deptrac, `composer audit`, `lint:twig`, `lint:container`, `doctrine:schema:validate`, пошук текстів без перекладу, `app:content:lint`, PHPUnit на реальному MySQL, зокрема SEO-тести за sitemap |
| frontend | ESLint, `tsc --noEmit`, Vitest із порогами покриття, `npm audit --audit-level=high`, бюджет бандла |
| image | hadolint, actionlint, збірка prod-образу, Trivy, запуск `compose.prod.yaml`, smoke-тест: `robots.txt`, sitemap, редирект із `www` |
| e2e | `make e2e`: prod-образ із MySQL окремим проєктом, Playwright на Mobile Chrome, Mobile Safari і Desktop, axe, бюджети Lighthouse у мобільному профілі |

SEO-тести за sitemap працюють у PHPUnit, а Lighthouse — на стеку `e2e`, тому окремого завдання `seo` немає: prod-образ не збирається двічі.

Завдання `frontend` запускає лише контейнер Node, тому не чекає на збірку PHP-образу.

**`deploy.yml`** просуває один і той самий образ середовищами:

| Подія | Результат |
| ----- | --------- |
| Merge у `main` | Образ `ghcr.io/iadmitrencko/self-fighter:<sha>` автоматично йде на staging |
| Git-тег `vX.Y.Z` | Той самий образ без перезбірки йде на production |
| Невдала перевірка після деплою | Автоматичний відкат до попереднього образу |

Послідовність на сервері через SSH:

1. `docker compose pull`
2. Міграції та `app:content:sync` в окремому контейнері
3. `docker compose up -d --wait`
4. Перевірка `/healthz`, `/` і `robots.txt`, за потреби відкат

Правила:

- Міграції сумісні з попередньою версією коду, інакше відкат небезпечний. API так само приймає запити від гри попередньої версії (розділ 3.7).
- Секрети, зокрема `GOOGLE_CLIENT_ID` і `GOOGLE_CLIENT_SECRET`, лежать у GitHub Environments і в `.env` на сервері, але не в Git.
- MySQL не публікується назовні.
- Дії GitHub закріплені за повним SHA, а інструменти запускаються з образів, закріплених за digest. Dependabot щомісяця пропонує оновлення дій.
- `aquasecurity/trivy-action` не використовуємо: у березні 2026 його теги були скомпрометовані (CVE-2026-33634). Trivy отримує лише архів образу, без Docker-сокета й токена.
- Образ збирається під архітектуру VPS. Локальна машина має arm64, тому dev-образ завжди будується локально.
- Перезапуск контейнера дає кілька секунд простою. Для MVP це прийнятно.

## 8. Тестування

| Вимога §17.3 | Рівень | Інструмент |
| ------------ | ------ | ---------- |
| Валідація, межі діапазонів, округлення | Модульні | Vitest |
| Випадкова генерація | Модульні, property-тести | Vitest, fast-check |
| Результати вправ, раундів, бою, обидва правила | Табличні | Vitest |
| Звичайна драбина й драбина з поверненням | Модульні | Vitest |
| Контракт сховища, буфер, черга надсилання, помилки мережі | Модульні | Vitest |
| Відповідність спроб JSON Schema | Property-тести | Vitest, fast-check |
| Повторне проходження, повні сценарії | E2E | Playwright |
| Публічні сторінки, sitemap, події | Функціональні | PHPUnit |
| API даних, cookie пристрою, вхід, ізоляція користувачів, експорт, видалення | Функціональні | PHPUnit |
| Вхід, об'єднання, черга надсилання | E2E | Playwright |

Справжній Google у тестах не викликаємо: вхід працює через підробленого постачальника OAuth. PHPUnit підставляє `tests/Account/FakeGoogle` на місце точки обміну коду, а `make e2e` запускає поруч із Playwright `e2e/fake-google.mjs` зі сторінкою вибору облікового запису й перевіркою PKCE.

Обов'язкові межові випадки:

- `M=1` на всіх рівнях, `M=90` на середньому дає 27–63, `M=100` відповідає таблиці §8.3.
- Ціль 10 і результати 9, 10, 11 за обома правилами (§6.5).
- Драбина: `max=1` із поверненням має один етап, `max=5` має дев'ять, провал на першому етапі дає максимальний пройдений етап 0.
- Подвійне підтвердження створює один запис.
- Перезавантаження під час бою не змінює значень суперника.
- Після видалення власної вправи історія й «Повторити» працюють зі знімка.
- Без згоди й після відмови сайт не надсилає жодної події.
- Кожен згенерований виклик проходить валідацію §11.5.
- Повторне об'єднання не створює дублікатів, а власні вправи з однаковою назвою зливаються.
- Спроба, завершена без мережі, надсилається один раз після відновлення зв'язку й не потрапляє до іншого користувача.
- Один користувач не може прочитати чи змінити дані іншого.
- Після видалення даних гостя чи облікового запису нічого не лишається, а події втрачають `user_id`.
- Публічні сторінки не встановлюють cookie.
- Перегляд сторінок і гри без жодного запису не створює гостя.
- Під час входу й виходу токен пристрою змінюється, а старий більше не діє.
- Перший вхід лишає дані гостя за тим самим `user_id`, а після виходу дані облікового запису недоступні.
- Поточна спроба іншої версії формату в буфері відкидається без збою гри.

## 9. Прогалини в дизайні

Усі сім файлів `design/*.dc.html` посилаються на `./support.js`, якого немає в репозиторії, тому прототипи не запускаються самостійно. Вони слугують еталоном структури, кольорів і логіки.

| Чого бракує | Рішення |
| ----------- | ------- |

| Вхід і дані користувача | Пропозиція увійти на екрані результату й в історії, екран облікового запису з експортом і видаленням даних, діалог об'єднання, позначка «очікує надсилання» |
| Футер | Додаємо навігацію для перелінковки |
| Контраст номерів режимів | `#5E626A` на `#1B1D21` дає 2,76:1. Замінюємо на `#8A8D94` з палітри макетів, це 5,08:1 |
| Розмір заголовка лендінгу | Слово «тренування» шрифтом Unbounded Black займає 7,96 em, тож за розмірів макета не вміщається ні на телефоні шириною 360 px (44 px), ні в колонці десктопа (92 px). Розмір `h1` залежить від ширини колонки через container queries |
| Примітка у футері | Макет каже, що дані гостя лежать лише в браузері, а це суперечить R21. Пишемо, що історія зберігається на сервері й прив'язана до браузера |
| «з» поруч із числами | У Manrope велика «З» майже не відрізняється від «3», а в Unbounded так само мала «з». У підписах великими літерами й у великих числах пишемо скісну риску: «Крок 1 / 2», «6 / 9» |
| Зміна кількості раундів | Макет відкидає значення при зменшенні. Зберігаємо їх до старту, щоб помилковий клік не стирав ручні цілі |
| «Перервати» | У макеті це пряме посилання. У бою гри це «Відступити» з підтвердженням (R12) |

## 10. Ризики

| Ризик | Наслідок | Що робимо |
| ----- | -------- | --------- |
| Гість очищує cookie або відкриває сайт в іншому браузері | Історія лишається на сервері, але гість до неї вже не дістанеться, що б'є по §2 | Пропозиція увійти після першого тренування й на екрані історії, пояснення на екрані облікового запису |
| Сервер недоступний | Історія й власні вправи не відкриваються | Розпочате тренування триває, а результат чекає в черзі. Зовнішній моніторинг доступності й бекапи (етап 10) |
| Боти чи зловмисник масово створюють гостей | Зростає таблиця `user` і навантаження на базу | Гість з'являється лише під час першого запису, `/api` закритий у `robots.txt`, створення гостей обмежене за частотою, покинуті гості видаляються |
| Пошук дасть трафік лише за місяці | §19 не вдасться перевірити на органічних користувачах | Перших користувачів залучаємо напряму |
| Запити-гіпотези не мають попиту | Контент не приносить трафіку | Перевірка в Keyword Planner до написання текстів, щотижневий розбір Search Console |
| Більшість екранів не мають макета | Затягування етапу 6 | Спільні блоки, повторне використання токенів |
| Згенеровані виклики сприйняті як масовий контент | Google може знизити не лише ці сторінки, а й увесь сайт | Критерії з розділу 6.2, публікація хвилями, контроль індексації |
| Частина відвідувачів відхилить аналітику | Показники §19 занижені | Трактуємо цифри як нижню межу й доповнюємо розмовами |
| Вимоги до банера взяті з рекомендацій EDPB, а не з юридичного висновку | Текст може потребувати уточнення | Якщо частка аудиторії з ЄС стане помітною, перевіряємо текст у юриста |
| Вхід розширює обсяг першої версії | Запуск зсувається приблизно на тиждень, а перевірка гіпотези §1.2 починається пізніше | Етап 9 незалежний: якщо часу забракне, запускаємось без нього |
| Сервер зберігає історію тренувань усіх користувачів і персональні дані облікових записів | Витік або втрата зачіпає реальних людей | Мінімум даних, токени Google не зберігаємо, у базі лише хеші токенів пристроїв, ізоляція за `user_id`, шифровані бекапи, перевірка відновлення, видалення даних |
| Вбудовані браузери застосунків, наприклад Telegram чи Instagram, можуть блокувати вхід Google | Частина людей не зможе увійти | Підказка відкрити сайт у звичайному браузері, гра працює і без входу |

Щодо Safari: після 7 днів користування браузером без взаємодії із сайтом WebKit видаляє все, що записали скрипти: `localStorage`, IndexedDB і cookie з JavaScript. Cookie, який сервер поставив у відповіді HTTP, це правило не зачіпає, якщо його не ставить сторонній сервер, схований за CNAME чи чужою IP-адресою. Cookie пристрою ставить той самий сервер, що віддає сторінки, тому історія гостя від цього правила не залежить, а в `localStorage` лежить лише короткочасний буфер. Поведінку перевіряємо на реальному iPhone разом із §18 (етап 10).

## 11. Що потрібно від власника проєкту

1. Обрати й купити домен.
2. Надати VPS і SSH-доступ.
3. Надати доступ до Google-акаунта для Search Console і Keyword Planner.
4. Визначити автора або рецензента текстів.
5. Надати контакт для політики приватності, умов користування й сторінки про проєкт.
6. Налаштувати Google Cloud за кроками нижче.
7. Увімкнути захист гілки `main` за кроками нижче.

### Захист гілки `main`

Налаштування доступне після першого запуску CI, бо назви перевірок з'являються лише тоді.

1. На GitHub відкрити Settings → Rules → Rulesets → New ruleset → New branch ruleset.
2. Задати назву `main`, Enforcement status: Active, а в Target branches обрати Include default branch.
3. Увімкнути Require a pull request before merging.
4. Увімкнути Require status checks to pass і додати `backend`, `frontend`, `image`.

Після цього прямі push у `main` не працюватимуть: зміни потрапляють туди лише через pull request.

### Налаштування Google Cloud

Спеціальних дозволів і оплати не потрібно. Повна перевірка застосунку теж не потрібна, бо ми просимо лише `openid`, `email` і `profile`. Для локальної розробки домен не потрібен: вистачає проєкту для розробки з адресою `localhost`.

1. Увімкнути двоетапну перевірку в акаунті Google.
2. Підтвердити домен у Search Console тим самим акаунтом.
3. Створити два проєкти: один для розробки й staging, другий для production.
4. У Google Auth Platform → Branding заповнити назву Self-Fighter, email підтримки, посилання на головну, політику приватності й умови користування, а також авторизований домен. Поки домену немає, посилання й домен лишаємо порожніми.
5. В Audience обрати External. У статусі Testing увійти можуть лише акаунти зі списку Test users, тож для розробки досить додати туди свої. У production натиснути Publish app, щоб увійти міг будь-хто.
6. У Data access додати `openid`, `email`, `profile`.
7. У Clients створити клієнта типу Web application з адресою повернення:
   - розробка: `http://localhost:8080/connect/google/check`;
   - staging: `https://staging.{домен}/connect/google/check`;
   - production: `https://{домен}/connect/google/check`.
8. Зберегти Client ID і Client Secret одразу, бо секрет показується один раз. Вони йдуть у GitHub Secrets і `.env` на сервері, але не в Git і не в чат.
9. Після запуску подати застосунок на перевірку бренду. Без неї вхід працює, але Google показує лише домен. Після схвалення натиснути Publish branding протягом 7 днів.
